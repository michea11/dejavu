# Flip Perspective Skill Design Spec

## 概述

**flip**: 在做设计决策、选方案、下结论时，刻意换一个角度重新审视当前结论，在敲定前发现盲区。

"换角度"不限于反面——可以是成本视角、时间视角、新人视角、简化视角…任何当前讨论中缺席的视角都行。关键是**跳出当前的思维框架**，而不是机械地站到对立面。

灵感来源：本次 gotcha 设计过程中，每个关键决策点都通过"换个角度"发现了之前忽略的问题。比如"匹配机制"从模型匹配换到 grep 匹配、"捕获方式"从自动换到手动，都不是简单的"反过来"，而是切到了另一个维度。

## 核心流程

```
当前有一个"初步结论"（设计方案、技术选型、架构决策…）
       │
       ▼
/flip  [或模型主动建议]
       │
       ▼
[模型判断当前讨论中缺席的视角是什么]
  不是机械地选对立面，而是问：
  "我们在讨论中一直用的是什么框架？有什么角度我们还没看过？"
       │
       ▼
[从那个缺席的视角重新审视结论]
       │
       ▼
[输出: 发现了什么之前没看到的东西]
       │
  ┌────┴────┐
  │ 有发现   │  无发现
  ▼         ▼
[修正结论]  "这个角度也看过，没问题"
```

## 命令

### /flip
对当前讨论中的最新结论做一次换角度审视。模型自己判断当前缺席的视角。

### /flip <具体结论>
对指定的结论做审视，例如 `/flip "用 redis 做缓存"`

## 何时用

模型应在以下时机主动建议 flip（不超过 hintLevel 限制）：

- 用户说"就这样吧"、"没问题了"、"确定了"时
- 选型/方案讨论看似达成共识时
- 设计 spec 即将完成时

## 审视视角

模型动态判断当前讨论中缺席的视角，不设固定清单。以下为常见方向的示例：

| 示例 | 问法 |
|---|---|
| **对立面** | "不做 X 会怎样？" |
| **成本** | "这要多花多少时间/钱？值得吗？" |
| **简化** | "能不能不做？能不能做更少？" |
| **时间** | "3 个月后回头看这个决定，会后悔什么？" |
| **新人** | "不了解上下文的人看到会疑惑什么？" |
| **极端** | "用户完全乱用时哪里会出错？" |
| **放大** | "如果要撑 10 倍量，哪里先崩？" |

每次 /flip 选取 1 个最可能发现盲区的角度，不堆砌。

## 输出格式

```
[从 X 的角度看]

发现: (一句话说发现的盲区)

如果确实是个问题: 建议修正
如果没问题: 承认当前结论成立
```

## 可配置项

| 参数 | 默认值 | 可选值 |
|---|---|---|
| `hintLevel` | `normal` | `off` 永不主动 / `normal` 关键决策时提示 / `high` 任何结论都追问 |

## 边界

- /flip 不是辩论，不为了反对而反对。如果换角度后结论仍然成立，就确认它
- /flip 不替代 brainstorming。brainstorming 是"探索可能性"，flip 是"审视已有结论"
- /flip 不做实现，只做审视。审视完回到原来的流程

## 与 gotcha 的关系

```
gotcha ── 踩坑记忆 ── "这个错上次见过"
flip   ── 换角度审视 ── "还没从什么角度看过？"

两者独立调用，互不依赖
```
